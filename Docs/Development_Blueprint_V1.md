# 第一版开发蓝图

## 1. 蓝图目标

本蓝图服务于一个非常明确的目标：在 `4 周` 内完成一个以战斗为核心、可完整通关的校园第一章。蓝图不追求“全功能设计完备”，只追求“按正确顺序完成最关键的东西”。

本蓝图默认采用以下策略：

- 先做 `战斗纵切`
- 再做 `章节流`
- 最后做 `平衡与包装`

## 2. 范围冻结项

第一版不讨论、也不排期以下内容：

- 背包与装备
- 多角色或多职业
- 复杂剧情演出
- 开放式探索地图
- 可破坏大场景系统
- 长期成长树
- 多阶段 Boss
- 高级 AI 协同行为

如果某个新点子不能帮助“更快完成完整章节”，则默认延期到后续版本。

## 4. 开发执行顺序

### 第一步：战斗可打

先在 `CombatTest` 场景里完成：

1. 玩家移动与摄像机
2. 锁定
3. 轻三连
4. 重攻击
5. 格挡
6. 闪避
7. 反击值与灵巧值累积
8. 闪避追击与格挡反击
9. 2 个技能
10. 一个近战敌人的完整对战闭环

在这一步没有成立之前，不进入正式章节搭建。

### 第二步：敌人与掉落可复用

完成一套统一敌人框架：

- 通用 `EnemyBrain`
- 通用 `EnemyStateMachine`
- 可配置的 `EnemyArchetypeSO`
- 通用伤害、受击、死亡、掉落组件

随后基于这套框架扩出：

- 近战兵
- 机动兵
- 远程兵

### 第三步：章节流程可跑通

完成章节系统最小闭环：

- 教学提示触发
- 五区动作灰盒：入口、宽场、窄廊、侧路/捷径、Boss 前厅/房；V2 已追加 public-safe 模块化灰盒层，用 primitive/proxy 强化入口门框、宽场侧栏、窄廊梁柱、侧路台阶和 Boss 前厅读路
- 五区地图数据层：`SO_Chapter01_MapDefinition` 记录区域目标、路线门、捷径、遭遇与奖励；侧路 `Zone04` 已有 `SideRouteCache` 可选奖励语义
- 区域门控
- 遭遇战触发与清场
- 检查点激活
- 关键物品门禁
- Boss 房进入
- 章节结算

### 第四步：Boss 成为最终考核

Boss 目标不是“炫”，而是“让玩家把战斗系统都用一遍”。因此 Boss 的设计顺序应为：

1. 读招清晰
2. 格挡可解
3. 闪避可解
4. 距离切换清晰
5. 惩罚与恢复窗口明确

### 第五步：调参与构建

最后一周只做：

- 战斗数值平衡
- 镜头修整
- 小型表现增强
- Bug 修复
- 双平台构建验证；发布候选构建入口固定为 `ReleaseCandidateBuildUtility`，先做 dry-run 输入检查，再分别产出 `Builds/ReleaseCandidate/Windows/TY_NEW.exe` 与 `Builds/ReleaseCandidate/Mac/TY_NEW.app`

不再增加新系统。

## 6. 第一版关键实现策略

### 6.1 玩家实现策略

- 使用 `CharacterController`
- 使用代码控制主移动与朝向
- 攻击期间仅允许受控位移
- 输入缓存时间固定为 `0.2 秒`
- 动作取消规则只保留必要组合，不做复杂自由取消

### 6.2 敌人实现策略

- 敌人移动统一使用 `NavMeshAgent`
- 每个敌人共享统一的感知、受击、死亡、掉落基类
- 差异主要来自配置和少量特化状态
- 同屏敌人数量控制在 `3-4`

### 6.3 关卡实现策略

- 优先使用灰盒和现成模块素材
- 用 TriggerVolume 驱动教学与门控
- 用 EncounterDefinitionSO 定义遭遇战
- 用 CheckpointDefinitionSO 管检查点
- 章节主流程保持单线

### 6.4 存档实现策略

第一版只存：

- 当前章节 ID
- 当前检查点 ID
- 已获得关键物品
- 已触发的固定成长节点
- 已清除遭遇战标记

第一版不存：

- 复杂世界可破坏状态
- 敌人逐帧位置
- 非必要临时对象状态

## 7. 资源与素材策略

### 必须遵守

- 优先选择风格一致的低多边形素材，而不是局部高质量但风格不统一的资产
- 动画素材优先统一来源，保证骨骼一致与重定向成本可控
- Boss 与玩家至少保证前摇清晰，不要求复杂表演

### 建议做法

- 场景素材使用同一套校园风低模包
- 玩家与敌人尽量使用兼容 Humanoid 的角色资源
- 特效先用简化版占位，最后一周再替换或强化
- 音效只做必要反馈：命中、格挡、闪避、死亡、检查点、Boss 进入

## 8. 砍功能梯度

当进度延迟时，按以下顺序砍：

1. 环境叙事与剧情文案
2. 非必要交互物
3. 额外掉落表现
4. Boss 第 5 招
5. 校舍内部多余房间
6. 第二个固定成长节点的演出包装

以下内容不可砍：

- 玩家核心战斗动作
- 三类普通敌人
- Boss
- 检查点恢复
- 自动存档
- 章节通关链路

## 9. 发布前检查

发布候选版本必须满足：

- Win/Mac 都能启动
- 无阻断级 Bug
- 无持续 Console Error
- 新开局与检查点恢复都能稳定通关
- Boss 战不出现卡死、脱战、无敌异常
- 锁定、格挡、闪避、技能均有可见反馈

## 10. 蓝图结论

第一版的关键不是“把 ARPG 能想到的系统都做进去”，而是用一个短章节证明这套战斗和推进框架是成立的。只要这套蓝图执行到位，后续扩展第二章、更多敌人、更多技能和更复杂 Boss 都有稳固基础。

## 附录：并行问题流

从 `2026-04-15` 起，项目新增一个与主开发蓝图并行执行的问题流，专门跟踪代码审查中发现的运行时缺陷、结构性风险和测试缺口。

执行规则如下：

- 主进程仍按本蓝图推进每周交付物，不随意被低优先级问题打断
- `P0` 问题必须在当前周里程碑结束前清零
- `P1` 问题允许并行处理，但不得拖到发布候选之后
- 所有问题的状态、处理建议与关闭标准，统一记录在 `Docs/Parallel_Issue_Track.md`

这个并行问题流的作用不是拖慢开发，而是保证后续章节扩展建立在可信、可测、可维护的主干之上。
