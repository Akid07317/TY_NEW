# 自动开发路线图

本文件用于给自动化开发提供一个稳定的读写锚点。

它不替代 `Docs/Development_Blueprint_V1.md` 的总蓝图，也不替代 `Docs/Parallel_Issue_Track.md` 的缺陷流；它负责把“当前大阶段、当前小阶段、接下来做什么、已经做完什么、验证结果如何”写成一份持续更新的人话路线图。

## 1. 自动化工作规则

每次自动化唤醒后，按下面顺序执行：

1. 先读取 `AGENT.md`
2. 再读取 `Docs/Project_Master_Document.md`
3. 再读取 `Docs/Development_Blueprint_V1.md`
4. 再读取 `Docs/Parallel_Issue_Track.md`
5. 再读取本文件，确认当前大阶段、小阶段与最近一次执行记录
6. 选择一个最小但完整的增量直接实装，不做无关重构
7. 对本次改动做相关验证
8. 回写本文件中的状态、完成记录、验证结果与下一步
9. 在线程总结里用通俗中文说明：做了什么、为什么这么做、验证结果怎样、下一步是什么

默认约束：

- 优先推进“第一章可玩闭环”，不是堆系统数量
- 优先做可落地的小步快跑，不做大范围重写
- 遇到阻塞先在本地独立调查两轮，再决定停下
- 不自动提交，不自动推送
- 总结必须让非当前上下文的人也能快速看懂

## 4. 标记规则

状态只使用以下几种：

- `Pending`：还没开始
- `In Progress`：正在推进
- `Mostly Done`：主体已成，但还需要一轮收口
- `Done`：当前阶段目标已经成立
- `Blocked`：被真实阻塞卡住，且已经做过两轮本地调查

每次自动化执行完成后，至少更新这三处：

1. 本文件顶部的“当前默认大阶段 / 小阶段”
2. “当前开发路线”表中的状态
3. “执行记录”中的一条新记录

如果本次发现判断变了，也要直接改写，不要保守维持旧状态。

## 6. 晨间总结要求

每次自动化在本线程里汇报时，默认按下面顺序写：

1. 这次主要做了什么
2. 为什么这一步是当前最优先
3. 改了哪些关键文件
4. 做了哪些验证，结果如何
5. 现在卡不卡，卡在哪里
6. 下一次自动化最应该接着做什么

总结要求：

- 说人话，不要只贴技术术语
- 不要只写“已完成若干优化”这种空话
- 要明确告诉你“现在项目推进到了哪一步”
- 如果失败，也要把失败原因和已经排除过的方向写清楚
